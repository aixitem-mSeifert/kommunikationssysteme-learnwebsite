Fehlererkennung auf Bitebene
• Idee für die Verwendung von Redundanz– Daten werden in Form eines Codes  übertragen– Ausnutzung der „Distanz“ zwischen gültigen Codewörtern,
d.h. nicht alle möglichen Bitkombinationen sind gültige Codewörter
• Hamming-Abstand– Anzahl unterschiedlicher Bits zweier Codewörter c1 und c2,
d.h. Anzahl der 1-Bits von c1 XOR c2.– Beispiel: d(10001001, 10110001) = 3– Hamming-Abstand D von vollständigem Code C :
D(C) := min{ d(c1,c2) | c1, c2 Î C; c1 ¹ c2 }

Hamming 
Codes   (I)
• Hamming-Abstand eines Codes bestimmt die Fähigkeit des Codes, Fehler zu erkennen und 
zu beheben– erkennen von e-Bit-Fehlern: Hamming-Abstand e+1 notwendig– beheben von e-Bit-Fehlern:  Hamming-Abstand 2e+1 notwendig
• Wenn wir also einen Hamming-Abstand von 3 haben, können wir 2-Bit-Fehler 
erkennen und 1-Bit-Fehler beheben

Hamming 
Codes   (II)
• Beispiele– Fehlererkennender Code
> Code mit einem einzigen Paritätsbit
> Hamming-Abstand des Codes = 2 
> Änderung eines einzelnen Bits erfordert Änderung des Paritätsbits)
> Erkennung eines 1-Bit-Fehler möglich
(tatsächlich sogar Fehler mit ungerader Anzahl von Bits)– Fehlerbehebender Code (vereinfacht)
> 00000 00000, 00000 11111,
11111 00000, 11111 11111
> Hamming-Abstand des Codes = 5
> Korrektur von 2-Bit-Fehlern möglich
> Beispiel: 00000 00
111 Þ 00000 11
> FEC (Forward Error Correction)

Prüfsummen: Cyclic Redundancy Check
• Sender und Empfänger einigen sich auf ein gemeinsam verwendetes Bitmuster der Länge  
r+1 Bit, das als Generator G bezeichnet wird. Das höchstwertige Bit hiervon ist 1 
• Konzept: Berechne die r CRC-bits R so, dass die d + r Bits (als Binärzahl interpretiert) mit 
der Modulo-2-Arithmetik genau durch G teilbar sind  – Empfänger kennt G, teilt <D,R> durch G.  Falls der Rest ungleich 0, so liegt ein Fehler vor!– Ethernet CRC kann Burst-Fehler von weniger als r+1 Bits und jede ungerade Fehlerzahl 
erkennen, aber keine Fehler beheben!

Fehlererkennung: ARQ (Automatic Repeat Request)
• Verwendung eines fehlererkennenden Codes (CRC)
• Fehler werden erkannt, können aber nicht korrigiert werden! Daher 
müssen verfälschte Daten neu angefordert werden. 
• Einführung einer Flusskontrolle (wie bei TCP: Sliding Window):
Ø Identifikation der Datenblöcke
Ø Quittierung von Blöcken durch den Empfänger
Ø Wiederholung fehlerhaft übertragener Blöcke
